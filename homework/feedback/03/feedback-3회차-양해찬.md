# 3회차 과제 평가 피드백 — 양해찬

> 평가 관점: 구체성 개선·업무 배분 개선·실용성 개선 3개  
> 평가 기준: 각 스킬 `[역할]` 섹션에 명시된 전문가 역할. 형식·섹션명 준수 여부는 평가 대상 아님  
> 모든 지적은 제출한 스킬·이전 프롬프트 원문의 실제 문구에 근거함

## 상세 피드백

#### 과제1 — 스킬 제작·개선

## 요약
### 잘된점
- 검증 임계값을 `최대 10초 동안 0.5초 간격으로 /health 폴링(최대 20회)`처럼 수치화하여 판정 가능하게 함 (구체성)
- Phase A ~ D 파이프라인에 `병렬 Agent로 동시 착수`와 `배리어: 양 트랙 산출물 확정 대기`를 함께 설계함 (업무배분)
- 완료조건을 `단계 6 검증 로그 첨부 — 정적 4종 + 스모크(/health 200 응답 코드·본문)`로 실행 증거 기반화함 (실용성)
### 보완할점
- `pushed:>{cutoff-date}`의 값·산출 규칙 미정의로 조사 범위가 실행마다 달라짐 → 기본값 명시 (구체성)
- 트랙 B1·B2 `담당은 모두 오지`로 전문성 분담이 아닌 병렬화 수단에 머묾 → 역할 기준 재배분 (업무배분)
- 검증 로그의 저장 경로가 미지정되어 사후 감사 불가 → 로그 파일 경로 고정 (실용성)

## 설명
### 구체성
- 잘된점: 이전프롬프트의 `주요 라이브러리를 포함한 requirements.txt 작성`·`주요 소스코드들 작성` 같은 모호 표현을  
  `fastapi`, `uvicorn[standard]`, `gunicorn`, `pydantic`(2 계열 정확버전) 열거와 `{app-package}/main.py` ~  
  `core/config.py` 5개 파일 지정으로 대체함. 수치·임계값은 `{bind-port}`=`8000`, `1024~65535 범위 정수`,  
  `stars:>500`, `최대 5개 저장소`, `workers=(2*os.cpu_count())+1`, `timeout=30`, `재작업은 최대 2회`,  
  `기동 로그(stderr) 마지막 20줄`로 촘촘히 박혀 있음. 판정 기준도 `종료코드 0`, `경고 0건`, `미검출=통과`,  
  `10초 내 200 미수신 시 스모크 실패로 판정`으로 조건문화됨
- 보완할점: `language:Python fastapi pushed:>{cutoff-date} stars:>500`에서 `{cutoff-date}`만 기본값 목록에서  
  빠져 있어, 이전프롬프트의 `최근 1년 사이 commit, push 이력`이라는 범위가 미정의 변수로 후퇴함.  
  → `{cutoff-date}`=`실행일-365일` 산출식을 기본값에 추가할 것. `ruff check results/` → `경고 0건`도 룰셋 지정이  
  없어 ruff 버전 변화에 따라 통과 여부가 흔들리므로 `results/ruff.toml`에 `select`·`line-length`를 고정하고  
  검증 시 `--config` 경로를 명시할 것. `pydantic`(2 계열 정확버전)의 선정 규칙도  
  `조사된 상위 5개 저장소 중 최다 사용 버전` 등으로 명문화할 것
### 실용성
- 잘된점: 이전프롬프트의 완료조건이 `소스코드 작성 및 검증 완료` 한 줄이었던 것에 비해, 스킬은  
  `(1) results/ 하위 파일 존재 확인` ~ `(6) __pycache__·.pyc·.ruff_cache·.pytest_cache 등 부산물이 없음`까지  
  6개 검증 항목으로 전개하고 `완료 보고는 람이의 검증 로그·체크리스트 결과(정적 4종 + 스모크 200)를 근거로만  
  수행`으로 못박음. 수동 개입도 `정적 검증 + 최소 스모크 테스트 배치 실행`과 `결함 발견 시 오지에게 재작업 요청`  
  루프로 자동화됨. 산출물은 `results/fastapi_app/`·`results/Dockerfile`·`results/system_arch.md`로 경로가 확정되고  
  `폴더째 복사 이관이 가능하게 구성`이라 가공 없이 사용 가능함
- 보완할점: `응답 코드·본문({"status":"ok"}) 로그 첨부`와 `확인 결과를 로그로 첨부`는 첨부 대상 위치가 미지정이어서  
  세션 종료 후 증거가 사라짐. → `results/verification.log` 경로를 고정하고 완료조건 (2)에 "해당 파일 존재+내용  
  확인"을 추가할 것. 스모크 명령이 `curl -s -o /dev/null -w "%{http_code}" ...`처럼 bash 문법 단독이며 PowerShell  
  예시는 6-(6)에만 병기되어 Windows 실행 시 폴링 단계가 막히므로 `Invoke-WebRequest -UseBasicParsing` 대안을  
  (5)에도 병기할 것. `results/ 밖 임시 가상환경은 검증 후 제거`는 재실행마다 전체 재설치를 유발하므로  
  `pip 캐시 디렉토리는 유지` 예외를 명시할 것
### 역할별 팀원 배분
- 잘된점: 이전프롬프트에는 `당신은 Python - FastAPI 개발 10년차 이상의 전문가임` 단일 역할만 있었으나, 스킬은  
  `환경 구성 엔지니어(오지)`·`검증 엔지니어(람이)`·`온보딩 문서 작가(소이)`로 단계 1 ~ 7을 분담함.  
  AGENTS.md 경력 서술과 배정 내용이 키워드 단위로 대응함 — 오지의 `Docker·DevContainer, 버전 관리 도구` ↔  
  단계 4 `Dockerfile`·`gunicorn.conf.py`, 람이의 `실행 증거 없는 완료 보고를 절대 허용하지 않음` ↔ 단계 6 및  
  `작성자 자기검증 금지`, 소이의 `명사체·객관적 기술 문서 스타일` ↔ 단계 7 `system_arch.md 작성(명사체 기술문서)`.  
  병렬화는 Phase B `2트랙을 병렬 Agent로 동시 착수`와 Phase C `단계 6(람이) ∥ 단계 7 초안(소이)`으로 도입되고,  
  `트랙 간 산출물 내용 의존 없음(경로·이름만 참조)`으로 독립성 근거까지 제시함
- 보완할점: Phase B가 `(담당은 모두 오지이나 독립 Agent 2개로 분리 실행)`이라 전문성 기준 분담이 아니라 동일 역할의  
  병렬 복제에 머묾. → AGENTS.md에 devops 역할이 없는 제약을 명시하고, B2(배포 인프라)에는 `비루트 사용자  
  (USER appuser)`·시크릿 미포함 검토를 람이의 보안 점검 항목으로 사전 배정해 트랙별 검증자를 분리할 것.  
  AGENTS.md 행동원칙 `세팅과 문서화 동시 진행`에 비해 소이 착수가 Phase C로 늦으므로 단계 1  
  `.temp/research_notes.md` 확정 직후 디렉토리 트리·파일별 역할 표 골격을 선작성하도록 당길 것.  
  클로니의 `중간 산출물 품질 검토`가 어디에도 배정되지 않아 Phase D가 검증자 단독 판단에 의존하므로  
  배리어 통과 시점에 게이트 승인 단계를 명시할 것
