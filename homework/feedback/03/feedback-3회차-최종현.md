# 3회차 과제 평가 피드백 — 최종현

> 평가 관점: 구체성 개선·업무 배분 개선·실용성 개선 3개  
> 평가 기준: 각 스킬 `[역할]` 섹션에 명시된 전문가 역할. 형식·섹션명 준수 여부는 평가 대상 아님  
> 모든 지적은 제출한 스킬·이전 프롬프트 원문의 실제 문구에 근거함

## 상세 피드백

#### 과제1 — 스킬 제작·개선

## 요약
### 잘된점
- 이전 `심각도(상/중/하)를 일관 기준으로 산정`을 `심각도 3축`과 상/중/하 조건문으로 대체함 (구체성)
- 점검 3인을 `Agent로 **병렬 호출**함(서로의 결과가 입력이 아니므로 대기 불필요)`로 팬아웃함 (업무배분)
- 발견표를 9컬럼으로 확장하며 `담당`·`영향 범위`를 추가해 수정 티켓 전환이 가능하게 함 (실용성)
### 보완할점
- `AskUserQuestion`을 지시하나 `allowed-tools`에 해당 도구가 없어 실행 중단 위험 → 도구 추가 또는 폴백 (실용성)
- 교차 검증이 `제출자가 아닌 멤버 1인 이상`으로만 규정 → 영역 쌍 고정 규칙 필요 (업무배분)
- `수정 난이도`의 등급 정의가 없어 P1 ~ P3 재현성 부족 → 난이도 등급 정의 및 매핑표 필요 (구체성)

## 설명
### 구체성
- 잘된점: 이전프롬프트의 `근거가 부족한 항목은 [추정]으로 표기함`이 스킬에서 `코드에서 재현됨 → **[확정]**` /  
  `서버 동작·빌드 설정을 봐야 등급이 정해짐 → **[확인필요]**` / `실행 조건에 의존해 코드로는 판단 불가 →  
  **[추정]**`의 3분기 조건문으로 대체됨. `1회 실행 상한: 파일 10개 또는 총 1,500라인`,  
  `코드 인용은 **최대 2줄**까지 허용함`, `확인 질문 1문장`처럼 임계값·건수가 단위와 함께 명시됨.  
  `상: 관리자 권한·토큰·계정 정보가 로그인하지 않은 사람에게 도달하며 추가 조건 없이 실현됨`과 조건부 병기 형식  
  `중(서버가 무인증 요청 허용 시 상)`으로 등급 산정이 재현 가능함. 안티예시로 `인증 처리가 미흡해 보임`을  
  금지 사례로 못박은 점도 모호어 차단에 기여함
- 보완할점: `**우선순위**: (심각도 × 수정 난이도 × 영향 범위)로 산정함. P1 즉시 / P2 차기 릴리스 / P3 백로그`에서  
  3개 인자 중 `수정 난이도`만 등급 정의가 없어 곱셈 결과가 평가자마다 달라짐.  
  → 심각도처럼 `수정 난이도 - 상: 공통 모듈 수정 + 회귀 테스트 필요 / 중: 단일 파일 수정 / 하: 설정값 변경`을  
  정의하고 `심각도 상 + 난이도 하 = P1`처럼 조합→P등급 매핑표를 3 ~ 5행으로 제시할 것.  
  사용자가 `1~4를 모두 포함`으로 답할 때 `파일 10개` 상한과 충돌하는 절단 규칙이 `우선순위 상위만 점검하고`로만  
  기술되어 있으므로 절단 단위(파일 단위인지 진입점 그룹 단위인지)를 명시할 것
### 실용성
- 잘된점: 이전프롬프트가 `<코드>`(점검 대상 관리자 페이지 프론트엔드 소스)`로 소스 붙여넣기를 요구한 반면, 스킬은  
  `Glob으로 대상 파일 목록·라인 수를 산출하고`와 `제외 패턴 기본값: **/node_modules/**, ...`로 입력 준비를  
  자동화함. `[재실행 시 처리]`의 `이전 산출물이 있으면 먼저 읽고, [확인필요] 항목의 답이 확보되었는지 확인함`은  
  반복 릴리스 점검에서 재입력 부담을 제거함. 산출물 경로가 `outputs/admin-page-review-{YYYYMMDD}.md` +  
  `동일 날짜 파일 존재 시 -{2}부터 순번을 붙임`으로 바뀌어 덮어쓰기 사고 없이 이력이 누적되며,  
  `대상 코드 리포지토리에는 어떤 파일도 생성·수정하지 않음`으로 점검 대상 오염을 차단함. 완료조건도  
  `모든 발견에 9개 컬럼이 채워짐`, `[확인필요] 항목마다 확인 질문이 1개 이상 작성됨`처럼 산출물 검사로 판정 가능함
- 보완할점: `[입력]`의 `사용자가 주지 않으면 AskUserQuestion으로 요청함`이 frontmatter  
  `allowed-tools: Read, Glob, Grep, Write, Agent`에 없는 도구를 지시함. 범위 미지정은 가장 흔한 실행 시나리오이므로  
  첫 실행에서 바로 막힐 수 있음. → allowed-tools에 AskUserQuestion을 추가하거나  
  `범위 미지정 시 진입점 우선순위 1~2를 기본 범위로 자동 적용하고 산출물에 "범위 자동 선정" 표기` 폴백을 명시할 것.  
  완료조건의 `토큰·비밀키·환경변수 값 미포함을 확인함`도 검증 방법이 없어 자기보고에 머무르므로  
  `Grep으로 금지 패턴(sk-, eyJ, VITE_.*=값) 0건 확인`처럼 확인 수단을 명기할 것
### 역할별 팀원 배분
- 잘된점: 이전프롬프트에도 4인 분담이 있었으나 스킬에서 `클로니(오케스트레이터): 점검 범위 확정·게이트 운영·최종  
  확정. 직접 점검은 하지 않음`이 추가되어 조율자와 실행자가 분리됨. AGENTS.md 경력 서술과 배정이 키워드 단위로  
  대응함 — 노출이 `프론트엔드 빌드 산출물의 비밀정보 노출 경로를 점검·차단한 경험` ↔ `환경변수의 번들 인라인 여부,  
  웹 스토리지 저장 항목`, 통신이 `API 클라이언트 공통화와 인증 실패 공통 처리를 설계·점검한 경험` ↔  
  `요청 서명 생성 규칙, 공통 에러 처리(응답 인터셉터)`, 정리 `심각도·영향 범위 기준으로 통합해 담당별 수정  
  티켓으로 전환한 경험` ↔ `심각도·영향 범위·담당·우선순위 산정, 기각 판정`. 협업 패턴은 계층형 + 병렬 팬아웃 +  
  배리어(교차 검증) + 파이프라인(정리 통합) 조합으로 작업 성격과 맞음
- 보완할점: `각 후보를 제출자가 아닌 멤버 1인 이상이 코드를 다시 읽어 재현·반증함`에서 검증자 선정 규칙이 없어  
  실행마다 배정이 달라지고 특정 멤버에 검증 부하가 쏠릴 수 있음. → `권한이↔통신이 상호 검증, 노출이 후보는  
  통신이 검증`처럼 영역 쌍을 고정하거나 `후보 제출 순번 기준 라운드로빈`을 명시할 것.  
  `**담당**: 프론트엔드 / 백엔드 / 인프라`의 담당 값이 AGENTS.md 멤버와 다른 축인데 매핑이 없어 발견을 낸 멤버와  
  티켓 수신자의 연결이 끊기므로, `유형 값` 10종별 기본 담당 지정표(예: `환경변수 노출 → 프론트엔드+인프라`)를  
  추가할 것. 게이트 실패(전 항목 기각) 시 재점검 여부도 정의되지 않아 종료 조건이 비어 있음
