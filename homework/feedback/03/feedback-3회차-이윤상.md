# 3회차 과제 평가 피드백 — 이윤상

> 평가 관점: 구체성 개선·업무 배분 개선·실용성 개선 3개  
> 평가 기준: 각 스킬 `[역할]` 섹션에 명시된 전문가 역할. 형식·섹션명 준수 여부는 평가 대상 아님  
> 모든 지적은 제출한 스킬·이전 프롬프트 원문의 실제 문구에 근거함

## 상세 피드백

#### 과제1 — 스킬 제작·개선

> `prompt.txt`가 `"I 0626 C1 000201 ~ I 0626 C1 000264" 사이의 값으로 바코드 생성해줘` 2줄 사용예시뿐이고  
> AGENTS.md도 부재하여, 판정 기준 1)은 스킬 자체의 절대 수준으로 판정함

## 요약
### 잘된점
- 레이아웃 기준값을 `888 × 293 px`/`65 px`/`49 pt`처럼 단위 포함 수치표로 고정해 재현 오차를 제거함
- `--prefix`/`--start`/`--end`/`--zip` CLI 인자화로 범위 요청을 명령 한 줄에 일괄 처리 가능함
- `textbbox` 오프셋 보정, 세로텍스트 90° 회전 등 실패 원인을 ❌/✅ 대비 코드로 못박아 재발을 차단함
### 보완할점
- 생성 후 바코드 판독 검증 절차가 없어 완료조건이 `완료: {len(created)}개 생성` 수준에 머묾 (실용성)
- 전문가 역할 정의가 전혀 없어 픽셀분석·스크립트·검증이 단일 주체에 뭉쳐 있음 (역할배분)
- 범위 수백 건 처리 시에도 `for num in range(...)` 순차 루프여서 병렬 처리 여지 미반영 (역할배분)

## 설명
### 구체성
- 잘된점: `| 바코드 너비 | 745 px |`, `| 헤더 폰트 크기 | 49 pt |`, `'module_width': 0.45`, `'dpi': 200`  
  등 값마다 px/pt 단위와 수치가 붙어 해석 여지가 없음(기준 2).  
  `next(r for r in range(h) if row_dark[r] < 200)`, `col_dark[c] < 150`, `row_m2m[r] < 248`처럼 판정  
  임계값이 조건문으로 명시됨(기준 3). `범위로 요청받으면(...) prefix(I 0626 C1)와 시작/끝 번호(265, 269)를  
  값에서 추출한다`처럼 입력 해석 규칙까지 검증 가능한 문장으로 기술함(기준 1)
- 보완할점: `이미 알고 있는 888×293 레이아웃이라면 이 단계는 건너뛰고`의 "알고 있는" 판별 기준이 미정의임.  
  → `입력 원본 PNG의 (width,height)==(888,293)이면 6장 생략, 아니면 필수 수행`처럼 조건식으로 대체할 것.  
  또한 `NNNNNN | 6자리 일련번호`에 상한 초과 시 처리 규칙이 없으므로 `--end > 999999면 오류 종료`를 명시할 것
### 실용성
- 잘된점: `pip install python-barcode pillow` 1회 후 `python generate_barcodes.py --prefix "I 0626 C1"  
  --start 265 --end 269 --output-dir ./output_barcodes --zip` 단일 명령으로 생성·압축까지 종료되어 수동  
  개입이 사실상 0단계임(기준 1). 산출물이 `f"{slug}_{num_str}.png"` 명명 규칙의 PNG와  
  `barcodes_output.zip`으로 확정되어 재가공이 불필요함(기준 2). Windows에 `zip` 셸 명령이 없는 점을  
  예견해 `zip_output.py`를 별도 제공한 점도 현장 적용성을 높임
- 보완할점: 완료 신호가 `print(f"완료: {len(created)}개 생성 -> {args.output_dir}")`뿐이라 "파일이 몇 개  
  만들어졌나"만 확인되고 "바코드가 읽히나"는 미검증임(기준 3 미충족). → `pyzbar`로 생성 PNG를 역디코딩해  
  `decode(img)[0].data == label_text`를 전 건 대조하고 `판독성공 N/N (100%)`를 출력하며, 불일치 1건이라도  
  있으면 exit code 1을 반환하도록 완료조건을 상향할 것. 원본 대비 레이아웃 검증도 `좌표 오차 ±2 px 이내`  
  등 수용범위를 명시할 것
### 역할별 팀원 배분
- 잘된점: 판정 기준 1) ~ 3) 모두 미충족이나, 작업 단계 자체는 `2. 레이아웃 기준값` → `4. 바코드 생성  
  스크립트` → `5. ZIP으로 묶기` → `6. 원본 이미지 픽셀 분석 방법` 순으로 분리돼 있어 역할 매핑의 골격은  
  이미 존재함. 이 골격에 담당자만 얹으면 단기간에 큰 폭의 개선이 가능한 상태임
- 보완할점: 문서 전체에 `[역할]` 섹션과 전문가 지정 문구가 한 줄도 없어 기준 1) 팀원별 분담과  
  기준 2) 협업 패턴 대응을 모두 판정할 수 없음. → `이미지분석가`(6장 픽셀 기준값 도출) →  
  `스크립트개발자`(4·5장 구현) → `품질검증자`(판독 검증) 파이프라인형으로 3역할을 명시할 것.  
  기준 3) 병렬 처리도 `for num in range(args.start, args.end + 1)` 순차 루프가 유일한 처리 경로여서  
  미충족임. 일련번호 간 의존성이 없으므로 `concurrent.futures.ProcessPoolExecutor`로 `generate_one`을  
  분할 실행하고 `--workers` 인자를 추가하면 예시 범위 `000201 ~ 000264`(64건) 이상 대량 요청에서  
  처리시간이 단축됨
