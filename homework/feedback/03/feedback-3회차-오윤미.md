# 3회차 과제 평가 피드백 — 오윤미

> 평가 관점: 구체성 개선·업무 배분 개선·실용성 개선 3개  
> 평가 기준: 각 스킬 `[역할]` 섹션에 명시된 전문가 역할. 형식·섹션명 준수 여부는 평가 대상 아님  
> 모든 지적은 제출한 스킬·이전 프롬프트 원문의 실제 문구에 근거함

## 상세 피드백

#### 과제1 — 스킬 제작·개선

> 접근상태: 프롬프트접근불가 — 레포 `prompts/`에 PKCS#11 주제 이전 원본 프롬프트가 없어  
> "기존 프롬프트 대비" 기준은 스킬 자체의 절대 수준으로 판정함

## 요약
### 잘된점
- 요구수준을 `1. 명세 필수` ~ `8. 확인 불가` 8분류로 고정하고 판정 조건문까지 명시해 해석 편차를 제거함 (구체성)
- 검색·버전·코드 적합성을 각각 다른 스킬로 이관해 위임 경계를 명확히 함 (업무배분)
- 출력 형식을 마크다운 템플릿(결론/공식 근거/요구 수준 표/확인 불가)으로 고정해 후가공이 불필요함 (실용성)
### 보완할점
- Base·Current Mechanisms·Profiles 원문 조회가 독립적인데 병렬 지시가 없어 순차 대기 발생 → 3병렬 명시 (업무배분)
- 완료조건·검증 절이 없어 산출물의 통과 여부를 제3자가 판정 불가 → 체크리스트 3항 추가 (실용성)
- 수치 기준이 `1~2문장`에 국한되어 최소 인용 건수·조회 문서 수 임계값이 부재함 (구체성)

## 설명
### 구체성
- 잘된점: 모호어 대신 판정 가능한 조건문을 사용함. `본문이 실제로 토큰이 *shall* 해야 한다고 적은 경우에만 1로  
  둔다`, `본문이 **명시적으로 금지한** 경우에만 2다`, `인용 조항에 연결할 수 없다면 추측하지 말고 **공식 문서로  
  결정 불가**로 분류한다`로 회색지대의 처리 방향까지 규정함. `(shall / must / required)`, `(may / optional)`,  
  `(implementation-dependent)` 등 요구수준 결정 단어를 8분류에 1:1 매핑하고, `필수 vs 토큰 제한 (1 vs 7)`,  
  `금지 vs 단지 요구되지 않음 (2 vs 3/8)` 두 경계 사례를 별도 분기로 명시함
- 보완할점: 수치 명시가 `1~2문장` 한 곳에 그쳐, 절차 2단계 `지배 원문을 가져온다`의 성공 임계값이 없음.  
  → `문서별 최소 1개 이상, 총 2개 이상의 doc:sec 인용을 확보하며, Profiles 미해당 시 "해당 없음"을 명시`처럼  
  건수 임계값을 절차에 추가할 것. `요구 수준` 표의 `근거` 열 형식도 `<doc:sec>`로만 제시되어 있으므로  
  `문서명:절번호:대상이름` 3요소 필수로 포맷을 고정하면 인용 누락을 기계적으로 검출 가능함
### 실용성
- 잘된점: `pkcs11-v240-spec-search로 지배 원문을 가져온다`부터 `결론 → 구현이 선택할 수 있는 범위 → 확인하지  
  못한 것 순으로 서술한다`까지 6단계가 도구 호출을 포함해 연속 실행되도록 기술되어 사용자 중간 개입이 불필요함.  
  범위 이탈 시 라우팅도 `어떤 용어가 v2.40에 아예 없다면 그것은 버전 문제다 → pkcs11-version-compatibility`로  
  자동화됨. `## 출력 형식`이 마크다운 코드블록 템플릿으로 제공되어 표·섹션 구조 그대로 문서에 붙여 쓸 수 있음
- 보완할점: 완료조건 절이 없음. `## 하지 말 것`은 `인용 없이 해석하기`처럼 금지사항 열거이며 완료 판정 기준이  
  아님. → `## 완료조건`을 추가하여 `요구 수준 표의 모든 행에 근거 doc:sec이 채워져 있음`,  
  `분류 8종 중 정확히 하나만 부여됨`, `Profiles 절이 인용 또는 "해당 없음"으로 채워짐` 3개 체크로 기술할 것.  
  산출물 저장 경로가 없어 재사용이 어려우므로 `docs/interpretations/{CKM명}-{일자}.md`로 저장 위치를 지정할 것
### 역할별 팀원 배분
- 잘된점: 단일 스킬이 모든 일을 하지 않고 3개 경계로 분담함. 근거 확보는 `pkcs11-v240-spec-search로 정확한  
  표현을 먼저 확보한 뒤`, 버전 판별은 `→ pkcs11-version-compatibility`, 코드 판정은 `구현 코드가 적합한지  
  판정하기 — 여기서는 **요구사항을 만들고**, 그것을 코드에 적용하는 것은 코드 리뷰 스킬의 일이다`로 명시적  
  이관됨. AGENTS.md 대응도 확인됨 — 규격조사가(써치)는 `base / current-mechanisms / profiles에서 원문 검색·인용.  
  판단은 하지 않음`, 규격해석가(저지)는 `shall과 may를 절대 섞지 않음`·`대응 스킬: pkcs11-v240-interpreter`로,  
  본 스킬의 `근거 먼저, 해석은 그 다음` 파이프라인형 패턴과 일치함
- 보완할점: 병렬 처리 지시가 없음. 절차 2단계는 `Base의 함수 조항과 Current Mechanisms의 mechanism 조항,  
  그리고 해당되면 profile 원문까지`를 한 단계에 묶었으나 세 문서 조회는 상호 의존이 없음. AGENTS.md의  
  `서로 독립적인 조사만 병렬 수행`·`병렬 조사자는 최대 3명`이 스킬 본문에 반영되지 않은 상태임.  
  → `2단계: Base / Current Mechanisms / Profiles 3개 조회를 spec-search에 동시 위임(최대 3병렬), 3개 응답 수집  
  후 3단계 진행`으로 명시할 것. AGENTS.md `4단계(검증): 크리틱이 ... 확인`도 스킬에 반영되지 않아 자기 검증  
  상태로 종료되므로 출력 직후 Critic 검토 호출 지점을 절차 6단계 뒤에 추가할 것
