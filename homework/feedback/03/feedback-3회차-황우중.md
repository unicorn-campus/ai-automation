# 3회차 과제 평가 피드백 — 황우중

> 평가 관점: 구체성 개선·업무 배분 개선·실용성 개선 3개  
> 평가 기준: 각 스킬 `[역할]` 섹션에 명시된 전문가 역할. 형식·섹션명 준수 여부는 평가 대상 아님  
> 모든 지적은 제출한 스킬·이전 프롬프트 원문의 실제 문구에 근거함

## 상세 피드백

#### 과제1 — 스킬 제작·개선

## 요약
### 잘된점
- 이전 `미상이면 자동 판별`류 모호 지시를 `파일 10개 이하`·`11개 이상`·`50개 초과` 등 임계값으로 전환함
- 심각도 5등급을 `인증 없이 원격 코드 실행`처럼 조건문으로 정의해 판정 재현성을 확보함
- 9개 카테고리를 병렬 스캔 단위로 삼고 파이프라인형(스캔→검증→보고)을 작업 성격에 대응시킴
### 보완할점
- 완료조건이 `보고서 파일 1개 생성`에 머물러 실행 결과 확인 수준에 미달함 (실용성)
- 이전 8번의 `samples/의 예시 취약 코드로 실행하여` 검증이 완료조건에서 빠지고 [예시]로 격하됨 (실용성)
- `심각도 하한` 입력이 [처리] 단계 어디에서 필터로 작동하는지 미기술로 배분 공백 존재함 (역할배분)

## 설명
### 구체성
- 잘된점: 이전 `점검 범위: {예: 전체 / 변경분(diff)만 / 특정 모듈}`의 예시 나열이 `기본값: 전체`로 확정되고,  
  `대상 파일이 50개를 초과하면 사용자에게 범위 축소를 제안`, `후보가 5건 이하면 인라인, 6건 이상이면 병렬`  
  처럼 임계값·건수로 대체됨(기준 1·2). `Critical: 인증 없이 원격 코드 실행/인증 우회/데이터 대량 유출이  
  가능` 등 5등급이 조건문으로 서술되어 등급 분류가 검증 가능해짐(기준 3)
- 보완할점: `심각도 하한: {Critical | High | Medium | Low} — 기본값: Low(전체 보고)`가 입력에만 있고  
  [처리] 4)의 `확정 항목을 심각도 내림차순 정렬` 단계에 하한 필터 적용 문구가 없음. → 4)에  
  `하한 미만 항목은 상세에서 제외하되 요약 건수에는 집계`처럼 처리 규칙을 1줄 추가할 것.  
  또한 `대상 파일 10개 이하(또는 단일 파일)`의 파일 수 산정 기준이 확장자 필터 적용 전인지 후인지  
  불명확하므로 `점검 대상 확장자 필터 적용 후 개수 기준`으로 못박을 것
### 실용성
- 잘된점: 이전 프롬프트에 없던 저장 경로가 `{PRJ-DIR}/reports/보안점검_{대상명}_{YYYYMMDD}.md`로 명시되어  
  별도 가공 없이 바로 공유 가능함(기준 2). 이전 `아래를 입력받는다. 누락 시 되묻는다`의 전면 문답이  
  `기본값: 전체`·`미상이면 확장자로 자동 판별`로 대체되어 수동 개입 단계가 줄어듦(기준 1).  
  `확정 취약점이 0건이어도 보고서를 생성함`은 재점검 신뢰성을 살린 실무 판단으로 평가함
- 보완할점: 완료조건 `{PRJ-DIR}/reports/ 에 보고서 파일 1개 생성`은 생성 확인 수준이며, 나머지  
  `각 확정 항목에 심각도·근거·수정방안이 기재됨`도 문서 내용 점검에 그침(기준 3 미충족). 특히 이전 프롬프트  
  8번의 `(테스트) samples/의 예시 취약 코드로 실행하여 알려진 취약점이 검출되는지 확인한다`가 완료조건에서  
  빠지고 [예시]의 `기대: ... 6건이 심각도별로 보고됨`으로 후퇴한 점이 아쉬움. → 완료조건에  
  `samples/vulnerable_example.py 실행 시 계획 취약점 6건 중 6건 검출을 확인`처럼 회귀 기준을 수치로 복원할 것
### 역할별 팀원 배분
- 잘된점: [처리] 각 단계에 `범위 확정(클로니)`·`스캔(스캐너)`·`검증(검증가)`·`취합·정렬·보고(정리)`로 담당자를  
  명시하고, [역할]에 `취약점 후보를 카테고리별로 광범위하게 탐지하는 보안 엔지니어`처럼 전문성을 부여함  
  (기준 1). AGENTS.md의 스캐너 `카테고리별로 광범위하게 수집`, 검증가 `실제 악용 시나리오로 검증하여  
  오탐을 걸러냅니다`가 각각 `9개 카테고리를 Task(Agent)로 병렬 위임`, `악용 시나리오(입력→경로→영향)가  
  성립하면 확정`과 키워드 단위로 대응하며, `협업 패턴: 파이프라인형(스캔→검증→보고)`이 단계 연쇄형 산출물  
  성격과 일치함(기준 2). 카테고리 스캔·항목 검증을 독립 단위로 보고 병렬을 도입한 점이 기준 3을 충족함
- 보완할점: 2)에 `9개 카테고리를 Task(Agent)로 병렬 위임(협업형 병렬 초안)`이라 적어 단계 전체 패턴  
  `파이프라인형`과 표기가 혼재함. AGENTS.md 정의상 협업형은 `여러 전문 영역이 상호 물려 공동 제작`이나  
  9개 카테고리 스캔은 상호 의존이 없는 동종 병렬임. → `파이프라인형(단계) + 스캔 단계 내 팬아웃 병렬`로  
  계층을 나눠 표기할 것. 또한 9개 카테고리가 모두 스캐너 1인 역할로 묶여 있어 `메모리 안전(C/C++)` 같은  
  이질 영역의 담당 구분이 없으므로, 스캐너를 언어군별(웹/시스템/인프라 설정) 3개 서브 역할로 쪼개  
  `대상 파일 11개 이상` 분기 시 배정하도록 규칙화할 것
