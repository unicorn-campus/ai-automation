# 3회차 과제 평가 피드백 — 장진석

> 평가 관점: 구체성 개선·업무 배분 개선·실용성 개선 3개  
> 평가 기준: 각 스킬 `[역할]` 섹션에 명시된 전문가 역할. 형식·섹션명 준수 여부는 평가 대상 아님  
> 모든 지적은 제출한 스킬·이전 프롬프트 원문의 실제 문구에 근거함

## 상세 피드백

#### 과제1 — 스킬 제작·개선

## 요약
### 잘된점
- `타임아웃 기본 600초(10분)`·`크기 > 500MB면 WARN`·`3초 간격 × 최대 20회(≈60초)` 등 임계값을 못박음 (구체성)
- `-p "0:$APP_PORT"` 랜덤 포트와 `trap 'docker rm -f "$name"' EXIT`로 포트 충돌·정리 개입을 제거함 (실용성)
- `[병렬]`/`[조인]`/`[게이트·순차]` 표기를 정의하고 사전점검 6항목·검증 2항목에 병렬을 적용함 (업무배분)
### 보완할점
- 역할 표가 가상 직군이고 AGENTS.md 팀원(`설계리`/`구현이`/`검증이`)에 미대응 → 실팀원 이름 배정 (업무배분)
- `단일 에이전트로 실행하되` + `멀티 에이전트로 위임할 경우` 조건부 선언에 그침 → 호출 대상 확정 기술 (업무배분)
- 이전프롬프트의 `실행 요약(응답으로 출력)`에 해당하는 통합 리포트 필드가 소실됨 → 필드 목록 복원 (실용성)

## 설명
### 구체성
- 잘된점: 이전프롬프트의 `docker images {image}:{tag} 로 생성 여부·이미지 크기 확인`, `레지스트리에 이미지 push  
  완료 확인` 같은 막연한 표현을 `docker image inspect <image>:<tag>` 종료코드 0, `docker push` 출력의  
  `digest: sha256:...` 존재로 치환함. 스모크 판정도 `문자열 완전일치가 아니라 HTTP 200 + 본문에 "status":"UP"  
  포함`으로 명문화함. `타임아웃 기본 600초(10분)`, `크기 > 500MB면 WARN`, `3초 간격 × 최대 20회(≈60초)`,  
  `docker logs --tail 50` 등 단위·임계값이 이전프롬프트에는 전무했으나 전 단계에 도입됨.  
  `크기 > 500MB면 WARN(실패 아님, 보고에만 경고)`로 WARN/실패를 분리하고  
  `Gradle의 *-plain.jar(비실행)는 제외하고, 실행 가능한 repackaged jar(BOOT-INF/ 포함)만 이미지에 쓴다` 등  
  조건문도 명시함
- 보완할점: 임계값 중 일부가 단일 경계로만 존재함. `크기 > 500MB면 WARN`은 등급 구간이 없어 900MB와 510MB가  
  동일 판정임. → `500MB 초과 WARN / 1GB 초과 FAIL` 2단 구간을 둘 것. `대형 프로젝트는 사용자가 상향 지정 가능`도  
  상한이 없어 무한 대기 여지가 있으므로 `최대 1800초` 같은 상한을 명시할 것.  
  `JDK 메이저가 요구와 불일치면 경고 후 중단`은 프로젝트 요구 버전을 못 읽는 경우의 처리가 비어 있으므로  
  `요구 버전 미검출 시 사용자 확인 후 진행` 분기를 추가할 것
### 실용성
- 잘된점: 이전프롬프트는 `docker run --rm -d -p 8080:8080 --name smoke`로 포트·컨테이너명을 고정해 포트 충돌 시  
  수동 수정이 필요했으나, 스킬은 `port=$(docker port "$name" "$APP_PORT" ...)`로 매핑을 조회하고  
  `name="smoke-$(date +%s)-$$"`로 이름을 고유화함. `포트·경로는 하드코딩 금지 — application.yml/properties의  
  server.port·management.server.port·context-path·actuator base-path를 읽어 URL 조립` 지시로 설정 편차 대응이  
  자동화됨. 산출물이 `실행 가능한 repackaged jar`, `Docker 이미지`, `build.log`로 각각 파일 형태로 명시되고,  
  완료조건이 `docker image inspect <image>:<tag> 종료코드 0`, `docker push 출력에 digest: sha256: 존재(주 신호)`로  
  이전프롬프트의 `docker images 목록에 존재`보다 검증 강도가 높음
- 보완할점: 완료조건의 `실행 가능한 repackaged jar 생성 확인(BOOT-INF/ 포함)`은 확인 명령이 없어 판정 재현이  
  어려움. → `unzip -l <jar> | grep -q BOOT-INF/` 같은 검증 명령을 명시할 것. 이전프롬프트의  
  `실행 요약(응답으로 출력): 빌드 성공/실패 · 테스트 통과 수 · 이미지 크기 · (푸시 시) 레지스트리 경로`가 사라지고  
  `[조인] 두 결과(메타·스모크)를 합쳐 보고`처럼 서술만 남아 보고 필드가 불확정이므로 고정 필드 표 형식을  
  재도입할 것. `.dockerignore가 없으면 ... 제외한 파일을 생성 권고`도 권고 수준이라 수동 개입이 남으므로  
  자동 생성 후 통보로 승격할 것
### 역할별 팀원 배분
- 잘된점: 이전프롬프트는 `당신은 JVM 빌드 자동화와 컨테이너 이미지 최적화에 능한 10년차 백엔드/DevOps  
  엔지니어임`으로 단일 페르소나였으나, 스킬은 `빌드 담당`·`테스트/품질 담당`·`컨테이너 담당`·`릴리스 담당`  
  4역할로 `담당`·`산출물` 열을 갖춘 표로 분해함. `아래 탐지는 모두 읽기 전용이라 병렬로 수행한 뒤 판정에서  
  합류한다`로 사전점검 6항목을 병렬화하고 `### 5. 이미지 검증 — [병렬] 메타 ∥ 스모크 → [조인] 리포트`로 독립 점검  
  2건을 병렬화함. 반대로 `테스트가 실패하면 절대 이미지 빌드로 진행하지 않는다(3→4는 순차 게이트, 병렬화 금지)`로  
  의존 구간은 직렬 고정함
- 보완할점: AGENTS.md 멤버는 `스킬 설계자`(`트리거·도구 경계·워크플로우 골격을 먼저 세움`),  
  `스킬 구현자`(`모호어를 검증 가능한 명령·기준으로 치환`), `검증자`(`완료조건을 실제로 점검하고 반례를 찾음`)인데,  
  스킬이 배정한 작업은 `애플리케이션 빌드(테스트 포함)`·`레지스트리 푸시` 등 빌드·릴리스 도메인이어서 멤버 성향  
  서술과 키워드 대응이 성립하지 않음. `1 사전점검=협업형(병렬 수집)`으로 표기했으나 AGENTS.md의 협업형은  
  `병렬 초안 → 클로니가 교차 전달 → 라운드 반복`이므로 라운드 반복이 없는 읽기전용 fan-out에는 정의가 어긋남.  
  → 해당 단계는 병렬 fan-out을 뜻하는 표기로 정정하거나 라운드 반복 절차를 추가할 것.  
  `단일 에이전트로 실행하되 내부적으로 ... 역할을 번갈아 맡는다`와 `멀티 에이전트로 위임할 경우` 가정법 서술은  
  AGENTS.md의 `패턴은 문서상 선언이 아니라 실제 Agent 호출로 실행함(정직한 보고)`과 상충하므로, 단계별로 위임  
  대상 팀원명과 전달할 `[입력]` 산출물을 확정 기술하여 선언이 아닌 실행 스펙으로 전환할 것
